# Decision log

Newest last. Each entry: what was decided, why, and the measurement or fact behind it.

1. **Reads come from NCBI's copy on AWS when ENA is slow** (2026-11-06). ENA moved about 1 Mbit/s over Aspera and 0.3 MB/s over https from three unrelated networks (utaka, D07, a home connection) and four files, at the same time as the AWS copy
   ran at 17-40 MB/s on one connection. Not a Georgia Tech firewall problem; no request to IT. `--source auto` probes Aspera and orders the sources; the other is the fallback.
2. **Every SRA run is checked against ENA.** vdb-validate; fasterq-dump's spot count against ENA's `read_count`; the first 1,000 reads (sequence and quality) against ENA's FASTQ. NCBI also distributes SRA Lite files with simplified qualities.
3. **ENA's `read_count` has no single meaning** (2026-11-06). ERR13389718: 109,512,218 = 2 x 54,756,109 spots (reads). ERR14734229: 40,613,306 against 40,650,256 spots (about pairs). All 8 runs measured have 0.04-0.40% MORE spots in SRA than ENA's count.
   The check tries both readings and accepts up to 1% more, rejects more than 0.1% fewer. ReadLength comes from the Run Info's AvgSpotLen, not from a guess. (The tolerance became 5% in entry 31.)
4. **Binned qualities are not a sign of SRA Lite.** ERR13389718 (HiSeq 2500) has 6 distinct quality symbols at ENA and at NCBI. Only one or two distinct symbols is treated as Lite-like. No instrument-based rule.
5. **The sheet is written cell by cell, never by whole worksheet** (setSampleDatabase rewrites worksheets and flattens formulas; two machines would overwrite each other). Runs are claimed before work; a claim expires after 6 h; an unreachable sheet
   does not stop a download (journal, replayed later). (Refined by entry 30: whole-sheet rewrites are allowed for single-writer bulk tools.)
6. **`DownloadDatabase` is a spreadsheet of its own**, one tab per Run Info file, so nothing that rewrites the SampleDatabase or the alignment sheets can touch it.
7. **Speeds measured:** D07 11 MB/s (8 connections); mzebra 104 MB/s for one download, about 150 MB/s for three; utaka 40 MB/s (single connection, curl). A run's .sra file is 70% of its FASTQ size; fasterq-dump 38 s; the uBAM conversion 12 min (D07).
   The upload of the uBAMs to Dropbox (about 3.7 TB for the 328 runs) is the likely limit: stage timings are in the sheet since v9d.
8. **The B chromosome is found by replicating Clark et al.'s coverage ratio on the project reference, not by lifting his blocks** (56% of his core sequence is on unplaced contigs of the old assembly).
9. **B-chromosome reads are downloaded through the SRA source** (`bchrom` download.source: auto) with ENA as the fallback; disk is reserved at 9x the ENA FASTQ size for the SRA route (.sra + uncompressed FASTQ + scratch).
10. **One module, one folder, contracts instead of imports** (SPEC.md). A module may import the package of an upstream module it depends on, never its internals.
11. **Module 03 is not moved with the others** because the alignment run on utaka uses the old file manager. The shim `cichlid_common.file_manager` finds the old one; the move is one later change. (Superseded by entry 43.)
12. **The new layout lives on a branch** until no job runs anywhere; the old script names keep working through wrappers for one release.
13. **Measurement and call are separate; the pilot sets the thresholds** (2026-11-08). A BAM is reduced to raw counts stored with the hash of the definition (`<sample>.panel.json`); genotypes come from a later call step, so a threshold can change without touching a BAM, and measurements made under different definitions are never mixed. LG5 (cuts 0.25 and 0.75) and the B chromosome (2.5 and 1.6) start with the midpoints of the expected values and are refit on the pilot cohort's own distributions.
14. **LG5 inversion: 954 interior SNV markers plus the right-breakpoint junction** (2026-11-08). GT3 carries the standard arrangement; neither OB assembly contains the standard interior. The right breakpoint (GT3 26,726,680) is unique sequence and genotypable (junction a and b present in the OB pools of both genera, 0 of 143 reads in BB pools); the left lies in a repeat. Markers: alleles shared by LatrZW and MezeOBm, clean in the BB pools and Luwino, at about the inverted fraction in the OB pools (held-out OB pool 0.53 and 0.57). Held-out BB-type pools are NOT clean (0.06-0.20), so a diploid fish is called on the median per-site fraction. SRR18083730 came back from ENA with no base qualities (Q0), so no base-quality filter is used anywhere.
15. **B chromosome: disk only, depth over 874 core blocks scaled by 12,000 sampled bins** (2026-11-08). The core set on GT3 (874 blocks, 1.40 Mb; tier A 836) comes from 12 carriers and 9 B-free pools; 94% of the blocks are on placed chromosomes, so dilution over repeats was not a problem. The genome-wide depth is estimated from evenly spaced 50 bp bins (their median non-zero value, as in the discovery) so that no whole-genome pass is needed; checked against the 21 tracks with `bchrom.validate_scale`, and to be checked against mosdepth on the first pilot BAM.
16. **Goals 1 to 3 copy sexloci's code instead of depending on it** (2026-11-08). The lab's IndelReadClassifier and the built-in sites (TE1, TE2, chr7ins) are copied byte-identical (md5 0ee7541e51610bb101a811ae7e8ac12d and 89ad7175765a70a14b9f9cacb4951146 of the bodies, pinned by tests; allele fingerprints 1957b81b6617, d2b75a3b30e2, 8b7b5cf1d8c7) so that 04 keeps one JSON contract, a definition hash and offline tests. sexloci stays the reference implementation, keeps the sheet writer and the retrospective runs it already does, and `sd_genotypes.parity` compares the two on the same samples.
17. **The aligner is minimap2 -x sr** (2026-11-08, confirmed by the lab). `VARIANTS.md` of sexloci 0.1.26 says the gsdf calibration (0.530, 0.268) is for bwa; that is wrong and the document should be corrected. The calibration therefore applies to the pilot alignments; `gsdf.call.fit_anchors` is there if a future pipeline differs.
18. **gsdf rules follow sexloci, the code the calibration was made with** (2026-11-08). A 5 kb bin belongs to a window when it starts inside it (the first 04 version took bins entirely inside and also read sexloci's 'outside calibrated range' as 2-4 copies; both were wrong); the estimate is rounded half to even and clipped to 1-6; flagged only below 0.6 or above 5.4; the junction ratio uses the first flank only. The junction cross-check stays as a separate, non-blocking `check_flags`.
19. **Retrospective measurement streams only the needed regions** (2026-11-08). Each module with a `regions(cfg)` can be measured on samples whose BAM is not on disk: a read-only `rclone serve http` on the Bamfiles folder and one `samtools view` per sample give a small BAM that the same measurement code reads (`sd_genotypes.retro`). Modules that read the whole BAM or megabases (B chromosome, LG5 inversion) are measured on disk only.

21. **First real-data check of goals 1 to 3** (2026-11-08). 18 samples streamed from `Bamfiles/Mzebra_GT3_NCBI/` with `retro` (no failures; numpy backend) and measured with `gsdf` and `te`: chr7ins in SAMEA117806076 63 ref : 6 alt (`0/0`) and TE1 in AG_567_1 2 : 5 (`0/1`, GQ 13.3) are exactly the counts sexloci reported; MC_049 and MC_060 are called 2 and 4 copies and both flagged, as in the MC family result; the Kingiri carriers are `1/1` and `0/1`; the non-carriers `0/0` or `./.`. 22. **The gsdf junction cross-check expected the wrong magnitude and is to be replaced** (2026-11-08). It assumed unique junction coverage / unique flank coverage = (copies - 2) / 2 (0.5 for three copies, 1.0 for four). In the MC family (sheet copy numbers) the ratio is at most 0.054 in 25 two-copy samples and has median 0.243 (0 to 0.442, zero in at least 10%) in 21 three-copy samples, at a median flank depth of 5.8x (minimum 2.5x); a 4-copy fish at 18x (SAMEA117806076) gives 0.00. Reads wholly inside the 500 bp window map ambiguously (the copies are 99.4% identical), so only spanning reads count, and at low depth zero is common. The check only sets `check_flags`, never the call. Replaced (2026-11-08) by a one-sided rule: a unique-read junction ratio above 0.15 in a sample called with two copies is reported as `junction_in_two_copy` (all 25 two-copy MC samples were at or below 0.054); a missing junction in a sample called with three or more copies is not checked, and `junction_implied_copies` was removed. A depth-aware missing-junction rule stays open until well-covered samples are measured (the full run over the sheet's samples, not started).

30. **Database rows are added at the end, in bulk; whole-sheet rewrites only with a single writer** (2026-11-07). Refines 5. The first run-by-run attempt of `--add-pending` stopped at Google's quota (60 reads per minute) after 26 rows, because every run re-read and rewrote both sheets and called rclone twice. `--add-pending --bulk` reads and writes the two sheets once (an identical result, tested), makes one `rclone lsjson` per project folder, saves a CSV backup and reads the sheets back. A tool that rewrites a whole worksheet says so and runs only when nothing else writes that sheet; multi-writer work stays cell by cell with claims (the DownloadDatabase).
31. **The SRA count tolerance is 5%** (2026-11-07). Refines 3. Over every run measured, SRA has 0.01% to 1.71% MORE spots than ENA and never fewer; the check accepts up to 5% more, rejects more than 0.1% fewer, and records the result per run in `ReadCountCheck`. Hypothesis, not verified: ENA's FASTQ leaves out some reads that SRA keeps.

45. **Every panel JSON records the BAM it was measured on** (2026-11-09; requested by 03, SPEC "Requests from 03 to 04"). Schema 2: `bam` is the file name and `bam_size_bytes` the size. Reason: samples are realigned when new runs are added and keep their file name (`<sample>.all.bam`), so the size is what tells a measurement of the old BAM from one of the new. The old fields could not do this: `bam` was an absolute path (specific to the machine) and, for samples measured through `retro`, pointed to a temporary regional BAM that is deleted afterwards, with that BAM's size. For streamed samples the identity is now that of the source BAM on Dropbox, read with an HTTP HEAD request (a one-byte range request if the server sends no length) before anything is fetched, so a missing BAM is reported as `no_bam` without a fetch. `bam_size` was renamed `bam_size_bytes`; schema 1 files are still read (a streamed one has no usable size: `unknown`); every call table carries the identity; `sd_genotypes.panel.identity` answers current / stale / unknown. Not done: `retro` still skips a sample that already has a JSON whatever BAM it was measured on (use `--refresh`); a name and a size are not a checksum (a header fingerprint or a checksum would be stronger).
